# Evidence

Everything in the body has to be true, and the diff is the only source that cannot be stale.

## Sourcing

```sh
BASE=$(git symbolic-ref --quiet --short refs/remotes/origin/HEAD 2>/dev/null | sed 's|origin/||')
BASE=${BASE:-main}

git diff --shortstat "origin/$BASE...HEAD"   # budget tier
git diff --stat      "origin/$BASE...HEAD"   # shape of the change
git diff             "origin/$BASE...HEAD"   # the truth
git log --oneline    "origin/$BASE..HEAD"    # context only
```

Note the three-dot form. `A...B` diffs against the merge base, which is what the PR will show; `A..B` diffs against the current tip of the base branch and will include unrelated work that landed while you were on the branch.

**Never source the description from commit messages.** They are a summary of a summary, they are frequently written before the change settled, and on a squash-merge repo they may describe an intermediate state that never shipped. Use them to understand sequence and intent, then verify every claim against the diff.

**Read the files where the diff hides intent.** A renamed function plus three updated call sites reads as "rename" only if you can see both ends. A deleted branch of a conditional reads as "removed code" until you notice the condition can no longer be false. When a hunk changes behaviour and you cannot tell what the behaviour *was*, open the file.

## Large and noisy diffs

Changed-line counts drive the budget tier, so vendored and generated churn can push a small change into the large tier and license a body it does not need. Separate them:

```sh
git diff --stat "origin/$BASE...HEAD" -- . \
  ':(exclude)**/*.lock' ':(exclude)**/package-lock.json' ':(exclude)**/go.sum' \
  ':(exclude)**/vendor/**' ':(exclude)**/*.pb.go' ':(exclude)**/dist/**' \
  ':(exclude)**/*.snap' ':(exclude)**/__snapshots__/**'
```

Use the **hand-written** total for the tier. Mention the generated churn in one line if a reviewer would otherwise be startled by the file count, and name the upstream cause — "lockfile regenerated by the dependency bump" — rather than leaving it to be discovered.

If a diff is genuinely too large to read, say so to the user and describe what you did read. Do not summarise a diff you skimmed; a confident description of a change you did not understand is worse than an honest partial one.

## What may be asserted

Only what you verified in this session.

| Claim | Requires |
|---|---|
| "Tests pass" | You ran them and saw them pass |
| "No behaviour change" | You read every hunk and can name why |
| "Faster / smaller / fewer requests" | A before and after measurement |
| "Backwards compatible" | You checked the callers, not just the signature |
| "Fixes #123" | The user or the branch told you the number |
| "Pre-existing failure" | You reproduced it on the base branch |

If you did not verify it, either verify it or leave it out. The middle option — hedged phrasing like "should not affect existing behaviour" — is the worst of the three: it reads as a claim to a reviewer and as a disclaimer to the author, so nobody checks it.

Where a reviewer will reasonably want a claim you cannot make, say what you did instead. "Ran the unit suite; did not exercise the staging path" is useful. Silence about the staging path is not.

## Behaviour changes deserve naming

The single most valuable thing a body can contain is the list of behaviours that change for someone who is not reading the diff. These are what break, and they are exactly what a diff does not show — a diff shows a conditional inverted, not the empty state that now renders where a spinner used to.

Walk the change from the outside in: what does a user see, what does a caller receive, what does an operator observe. Anything that differs goes in the body, in plain language, whether or not it was the point of the change. Especially if it was not the point of the change.
