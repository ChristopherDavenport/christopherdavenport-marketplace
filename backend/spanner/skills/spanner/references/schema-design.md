# Schema Design — Primary Keys, Hotspots, Sharding

Spanner is a horizontally partitioned, externally consistent SQL database. The only knob that decides whether your writes scale is the **shape of the primary key**. Almost every "Spanner is slow" thread eventually traces back to a leading PK column whose values increase monotonically over time, packing all writes onto one split.

This reference covers how to choose primary keys, the four hotspot-safe key generation strategies, and the schema-level decisions you cannot reverse later.

## The Hotspot Rule

Spanner stores rows in **lexicographic primary-key order**, broken into contiguous ranges called **splits**. Each split is owned by one server at a time. If your leading PK column always increases (or always decreases), every new row lands in the same split, and only one server takes writes regardless of how many nodes the instance has.

This applies equally to:

- Primary keys of tables.
- Leading columns of **non-interleaved** secondary indexes (indexes are stored as tables internally).

Symptoms:

- Write QPS plateaus and adding nodes does nothing.
- The Cloud Console "Latency by key range" / "CPU by key range" charts show one red band.
- Tail latency on writes climbs while CPU on most nodes is idle.

## Anti-Patterns to Reject on Sight

| Anti-pattern | Why it fails |
|---|---|
| `PRIMARY KEY (CreatedAt, ...)` where `CreatedAt` is a timestamp | All inserts target the latest split |
| `PRIMARY KEY (Id)` where `Id` is `IDENTITY` *without* `BIT_REVERSED_POSITIVE` | Spanner does not support monotonic generation safely; sequential IDs hotspot |
| `PRIMARY KEY (Id)` migrated as-is from `SERIAL` / `AUTO_INCREMENT` / `IDENTITY` from PostgreSQL or MySQL | Same root cause |
| `PRIMARY KEY (UuidV1)` | UUIDv1 contains a timestamp prefix → still monotonic |
| `CREATE INDEX X ON T(commit_ts)` | Index leading column is monotonic; same hotspot, hidden |

## Safe Primary Key Strategies

Pick whichever fits the access pattern. All four spread writes uniformly.

### 1. UUIDv4 (`NEW_UUID()` / `gen_random_uuid()`)

Best for new tables where you don't need integer IDs and don't care about ordering by insert time.

```sql
-- GoogleSQL
CREATE TABLE Users (
  UserId STRING(36) NOT NULL DEFAULT (NEW_UUID()),
  Email  STRING(MAX) NOT NULL,
  ...
) PRIMARY KEY (UserId);
```

```sql
-- PostgreSQL dialect
CREATE TABLE users (
  user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email   TEXT NOT NULL
);
```

Notes:

- Use **v4** (random). Never v1 (timestamp-based — still monotonic).
- Storage cost: 16 bytes binary, 36 bytes as `STRING(36)` text representation.
- Collision probability is negligible (~1 billion UUIDs/sec for 86 years to hit 50% chance).
- You can mix client-generated and server-generated UUIDs as long as clients use the lowercase RFC 4122 representation.

### 2. `IDENTITY` Column with `BIT_REVERSED_POSITIVE`

Best when you need INT64 keys (joins, foreign-key targets, smaller storage than UUID).

```sql
CREATE TABLE Orders (
  OrderId INT64 GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE),
  CustomerId INT64 NOT NULL,
  ...
) PRIMARY KEY (OrderId);
```

The bit-reversal scrambles the underlying sequence value so consecutive IDs land in different splits. The sequence backing the column is dropped automatically when you drop the column.

### 3. Bit-Reversed Sequences (Manual)

Use when you need to share one sequence across multiple columns or want explicit control:

```sql
CREATE SEQUENCE OrderIdSeq OPTIONS (sequence_kind = 'bit_reversed_positive');

CREATE TABLE Orders (
  OrderId INT64 NOT NULL DEFAULT (GET_NEXT_SEQUENCE_VALUE(SEQUENCE OrderIdSeq)),
  ...
) PRIMARY KEY (OrderId);
```

PostgreSQL dialect uses `nextval('order_id_seq')` and the sequence kind is `bit_reversed_positive` in the `CREATE SEQUENCE` options.

### 4. Hash-Sharded Composite Key

Best when the natural key really is monotonic (event time, version number) and you still want to range-scan recent rows. Prefix the key with a small `ShardId` derived from a stable hash:

```sql
CREATE TABLE EventLog (
  ShardId   INT64 NOT NULL
    AS (MOD(FARM_FINGERPRINT(CAST(EventTime AS STRING)), 2048)) STORED,
  EventTime TIMESTAMP NOT NULL,
  UserId    INT64 NOT NULL,
  Payload   STRING(MAX),
) PRIMARY KEY (ShardId, EventTime DESC, UserId);
```

How to choose `N` (the modulus):

- Start with **N ≈ number of nodes × 2 to 10**. Too few shards → still hot. Too many → kills locality and scan efficiency.
- For a 3-node instance, `N = 32` to `N = 256` is reasonable. For 100 nodes, `N = 1024` to `N = 4096`.
- Use `FARM_FINGERPRINT()` (deterministic, well-distributed) — not `RAND()` (you couldn't query a single row again).
- Range queries must fan out across all `N` shards: `WHERE ShardId BETWEEN 0 AND 2047 AND EventTime > ...`. Build this into your query layer.

### Combining Strategies

For a child table that always needs to be read with a parent, use the parent ID as the leading key (which is already well-distributed if the parent uses one of the strategies above):

```sql
CREATE TABLE OrderLines (
  OrderId   INT64 NOT NULL,   -- already bit-reversed → no hotspot
  LineId    INT64 NOT NULL,
  ProductId INT64 NOT NULL,
  Quantity  INT64 NOT NULL,
) PRIMARY KEY (OrderId, LineId),
  INTERLEAVE IN PARENT Orders ON DELETE CASCADE;
```

The leading column inherits its distribution from the parent — no need to bit-reverse again.

## Key Reordering: Move the Monotonic Column

If you must keep a timestamp in the key, move it out of the leading position:

```sql
-- Bad: hotspot on the latest UserId-ish bucket then on every minute boundary
PRIMARY KEY (LastAccess, UserId)

-- Good: writes spread across UserId; per-user history is still range-scannable
PRIMARY KEY (UserId, LastAccess DESC)
```

`DESC` on `LastAccess` keeps the newest rows adjacent under each user, optimizing `LIMIT N` queries that want recent activity.

## DESC Timestamp Trick

`DESC` does not affect distribution (the column is just stored in inverted order); it affects scan efficiency:

```sql
CREATE TABLE UserSessions (
  UserId      INT64 NOT NULL,
  StartedAt   TIMESTAMP NOT NULL,
  ...
) PRIMARY KEY (UserId, StartedAt DESC);

-- Efficient: reads adjacent rows, no sort
SELECT * FROM UserSessions
WHERE UserId = @user
ORDER BY StartedAt DESC
LIMIT 20;
```

Without `DESC` on the column, the same query needs a sort that may spill.

## Surrogate vs Natural Keys

Prefer surrogate keys (UUID, bit-reversed integer) when:

- The natural key is monotonic (timestamp, sequence, version).
- The natural key may change (email, slug).
- The natural key is wide (multi-column composite).

Use a natural key when:

- It's stable and well-distributed (e.g., a hash already used as an external identifier).
- Lookups are always by that natural key (saves a join through a surrogate).

Composite keys are first-class — `(CustomerId, OrderId, LineId)` is normal Spanner.

## Type and Structural Limits

| Limit | Value |
|---|---|
| Maximum interleaving depth | 7 levels |
| Primary key column count | 16 columns |
| Total key size | 8 KB |
| `ARRAY` columns in primary keys / index keys | Not allowed |
| `JSON` columns in primary keys / index keys | Not allowed |

If you tried to put an `ARRAY<INT64>` in a primary key, schema creation fails. Use a separate child table interleaved into the parent instead.

## NULL in Primary Keys

GoogleSQL allows NULL in primary keys if the column is **not** declared `NOT NULL`. PostgreSQL dialect (and most reasonable schema designs) does not. Allowing NULL in PKs creates surprising sort behavior — leave `NOT NULL` on PK columns unless you have a specific reason.

## Multi-Tenant Patterns

Two common shapes; pick based on isolation requirements.

### Shared schema with tenant prefix (preferred default)

```sql
CREATE TABLE Singers (
  CustomerId INT64 NOT NULL,
  SingerId   STRING(36) NOT NULL DEFAULT (NEW_UUID()),
  FirstName  STRING(1024),
  ...
) PRIMARY KEY (CustomerId, SingerId);
```

- One database, one schema, all customers share tables.
- `CustomerId` as the leading key gives natural data locality per tenant.
- Cheap to add tenants. Easy backups. Schema changes apply to all tenants atomically.
- Application layer must always include `CustomerId` in `WHERE`. Add a "no tenant predicate" lint at query review time.

### Database per tenant

- Hard isolation; each tenant has independent backups, IAM, encryption keys.
- **Hits limits fast**: there is a quota on databases per instance, and schema changes propagate per-database (slow at scale).
- Use only when compliance / blast-radius requirements force it.

## Common Pitfalls

- **Migrating a Postgres `SERIAL` PK directly.** Convert to UUID or bit-reversed; do not just rename the column.
- **Picking too small an `N` for hash sharding.** Test with synthetic load — if one shard takes >10% of writes, increase `N`.
- **Putting a `commit_ts` column in the leading PK position.** Even one such table can pin a node. Shard or move the column.
- **Indexing a monotonic column with a non-interleaved index.** Same hotspot risk as a monotonic PK. Either don't index, or interleave the index into a parent that's well-distributed, or shard the index.
- **Assuming UUID storage is free.** `STRING(36)` UUIDs are 36 bytes per row × every index that includes them. For very wide tables, storing as `BYTES(16)` saves significant disk.
- **Using `CURRENT_TIMESTAMP()` as a default for a key column.** Both monotonic and not exactly the commit time. Use `spanner.CommitTimestamp` (Go) / `PENDING_COMMIT_TIMESTAMP()` (SQL) — and **only on non-key columns**.
