## The Problem: Sequential Key Hotspotting

Your auto-increment identity column is creating a **hotspot on a single split boundary**. This is a classic Cloud Spanner anti-pattern.

### Why This Happens

Cloud Spanner distributes data by sharding rows across splits based on key ranges. With a sequential integer key:

```
Node 1          Node 2          Node 3
[1 ... 1000]   [1001 ... 2000] [2001 ... 3000]
     ↑
ALL writes go here (always the "hot" end)
```

Every new row gets the next integer, so **all writes always hit the same split** — adding nodes does nothing because the work never distributes.

---

## Solutions

### Option 1: Bit-Reverse the Key (Recommended for keeping INT64)

Reverse the bits of the sequence value so writes scatter across the key space:

```sql
-- Schema
CREATE TABLE MyTable (
  Id INT64 DEFAULT (GET_NEXT_SEQUENCE_VALUE(SEQUENCE MySeq)),
  Data STRING(MAX),
) PRIMARY KEY (Id);

CREATE SEQUENCE MySeq OPTIONS (
  sequence_kind = 'bit_reversed_positive'  -- ← This is the key
);
```

> **`bit_reversed_positive` is the built-in Spanner solution** — it's specifically designed for this problem. The values are still unique and INT64, but they're distributed across the key space.

```
Before (sequential):  1, 2, 3, 4, 5 ...
After (bit-reversed): 4611686018427387904, 2305843009213693952, 6917529027641081856 ...
```

Writes now scatter across all splits → all nodes get work.

---

### Option 2: Use a UUID Primary Key

```sql
CREATE TABLE MyTable (
  Id STRING(36) DEFAULT (GENERATE_UUID()),
  Data STRING(MAX),
) PRIMARY KEY (Id);
```

**Pros:** Simple, universally understood  
**Cons:** Larger storage, slightly slower reads by PK, string comparison

---

### Option 3: Hash Prefix Sharding (Legacy approach, avoid if possible)

```sql
CREATE TABLE MyTable (
  ShardId INT64 NOT NULL,  -- hash(Id) % N
  Id INT64 NOT NULL,
  Data STRING(MAX),
) PRIMARY KEY (ShardId, Id);
```

**Cons:** Application must compute shard, range scans become complex — only use if you need a specific shard count for predictable distribution.

---

## Recommended Fix

```sql
-- Drop the old sequence/table, recreate with:
CREATE SEQUENCE MySeq OPTIONS (
  sequence_kind = 'bit_reversed_positive'
);

CREATE TABLE MyTable (
  Id INT64 DEFAULT (GET_NEXT_SEQUENCE_VALUE(SEQUENCE MySeq)),
  Data STRING(MAX),
) PRIMARY KEY (Id);
```

```

→ "Hot Tablet" metric should drop to near zero

→ Write QPS should scale linearly with node count
```

## What's happening: a hotspot on a monotonic key

`GENERATED BY DEFAULT AS IDENTITY` without `BIT_REVERSED_POSITIVE` produces sequential integers (1, 2, 3, …). Spanner splits data by key range, so all new rows land on the **same split** — the one that owns the current high-water mark. No matter how many nodes you add, every write is serialized through that one split. This is the classic Spanner hotspot.

---

## How to confirm it

Run this distribution check. A healthy table shows roughly equal counts across buckets; a hotspot shows nearly all rows in one bucket.

```sql
SELECT
  MOD(ABS(FARM_FINGERPRINT(CAST(Id AS STRING))), 20) AS bucket,
  COUNT(*) AS row_count
FROM YourTable
GROUP BY bucket
ORDER BY bucket;
```

If one bucket dominates, you have a hotspot. Also check **Spanner Studio → Key Visualizer** in the Cloud Console — a single bright horizontal band across time is the visual signature.

---

## Fix 1 (preferred): Switch to a bit-reversed identity column

This is the cleanest fix for a surrogate key. Bit-reversing the sequence value scatters writes across the key space while keeping the column auto-generated and opaque to callers.

```sql
ALTER TABLE YourTable
  ALTER COLUMN Id INT64 GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE);
```

> **Caveat:** `ALTER COLUMN` on an identity column is only supported if the table is empty or the change is compatible. For a live table you'll need to migrate (see Fix 3 below).

For a **new table**, write it correctly from the start:

```sql
CREATE TABLE Orders (
  Id      INT64 GENERATED BY DEFAULT AS IDENTITY (BIT_REVERSED_POSITIVE),
  UserId  STRING(36) NOT NULL,
  Amount  NUMERIC    NOT NULL,
  Created TIMESTAMP  NOT NULL OPTIONS (allow_commit_timestamp = true),
) PRIMARY KEY (Id);
```

---

## Fix 2: Switch to UUIDs

UUIDs are random by construction and distribute writes uniformly. Use Spanner's built-in function so the database generates the value — no application change needed for inserts that omit the column.

```sql
CREATE TABLE Orders (
  Id      STRING(36) DEFAULT (NEW_UUID()),  -- GoogleSQL
  UserId  STRING(36) NOT NULL,
  Amount  NUMERIC    NOT NULL,
  Created TIMESTAMP  NOT NULL OPTIONS (allow_commit_timestamp = true),
) PRIMARY KEY (Id);
```

Trade-off: `STRING(36)` is slightly larger than `INT64`, and UUIDs are not sortable by creation time.

---

## Fix 3: Hash-shard prefix (when you must keep a time/sequence component)

If callers need the ordering that a sequential key provides (e.g., for cursor-based pagination), prepend a hash shard so writes spread across N splits while the sequence is preserved within each shard.

```sql
CREATE TABLE Events (
  ShardId   INT64     NOT NULL,  -- MOD(FARM_FINGERPRINT(...), N)
  EventTime TIMESTAMP NOT NULL,
  EventId   INT64     NOT NULL GENERATED BY DEFAULT AS IDENTITY,
  Payload   JSON,
) PRIMARY KEY (ShardId, EventTime DESC, EventId);
```

Compute `ShardId` in your application or a generated column:

```sql
-- Generated column approach (N=16 shards)
ShardId INT64 NOT NULL
  AS (MOD(ABS(FARM_FINGERPRINT(CAST(EventId AS STRING))), 16)) STORED,
```

Queries must include all shards when you don't know which shard a row is on:

```sql
-- Fan-out query across all shards
SELECT * FROM Events
WHERE ShardId IN UNNEST(GENERATE_ARRAY(0, 15))
  AND EventTime > @cutoff
ORDER BY EventTime DESC
LIMIT 100;
```

Choose N to be roughly equal to your node count (or a small multiple). Too small and you still get hotspots; too large and fan-out queries become expensive.

## Migrating a live table

You can't change a primary key column type in place on a populated table. The standard approach:

1. **Create a new table** with the correct key scheme.
2. **Dual-write** to both tables from your application.
3. **Backfill** old rows using Dataflow or partitioned DML.
4. **Validate** row counts and spot-check data.
5. **Cut over** reads to the new table, then drop the old one.

For the backfill, use partitioned DML or Dataflow — not a single transaction, which would hit the 80,000-mutation / 100 MiB limits:

```sql
-- Partitioned DML backfill (idempotent, runs in parallel partitions)
UPDATE NewOrders SET migrated = TRUE WHERE migrated IS NULL;
```

# Cloud Spanner Write Throughput Bottleneck

You've hit a classic **hot shard problem** caused by your monotonically increasing primary key.

## The Problem

When you use `GENERATED BY DEFAULT AS IDENTITY`, new rows get sequential IDs like 1, 2, 3, 4... This means:

1. **All writes go to the same shard** - Sequential IDs cluster together in the key range
2. **One node becomes a bottleneck** - That node handles all writes while others sit idle
3. **Adding nodes doesn't help** - The hot shard can't be split further (it's already at the end of the key range)

This is a fundamental limitation of Spanner's range-based sharding with monotonic keys.

## Solutions

### Option 1: Randomize the Primary Key (Recommended)

Use a **hash-based or random prefix** to distribute writes across shards:

```sql
CREATE TABLE MyTable (
  Id INT64 NOT NULL,
  Shard INT64 NOT NULL,
  Data STRING(MAX),
  PRIMARY KEY (Shard, Id)
);
```

When inserting, compute `Shard = RAND() % 256` (or similar):

```sql
INSERT INTO MyTable (Shard, Id, Data) 
VALUES (MOD(ABS(FARM_FINGERPRINT(GENERATE_UUID())), 256), 
        GENERATE_UNIQUE_ID(), 
        'data');
```

Or use a UUID as the primary key:

```sql
CREATE TABLE MyTable (
  Id STRING(36) NOT NULL,
  Data STRING(MAX),
  PRIMARY KEY (Id)
);
```

```sql
INSERT INTO MyTable (Id, Data) 
VALUES (GENERATE_UUID(), 'data');
```

### Option 2: Use a Composite Key with Time-Based Prefix

```sql
CREATE TABLE MyTable (
  Timestamp INT64 NOT NULL,  -- milliseconds, bucketed
  SequenceId INT64 NOT NULL,
  Data STRING(MAX),
  PRIMARY KEY (Timestamp, SequenceId)
);
```

This distributes writes across time buckets.

### Option 3: Add a Hash Prefix Column

```sql
CREATE TABLE MyTable (
  HashPrefix INT64 NOT NULL,  -- RAND() % 256
  Id INT64 NOT NULL,
  Data STRING(MAX),
  PRIMARY KEY (HashPrefix, Id)
);
```

## Verification

Check if you're hitting the hot shard limit:

```sql
SELECT 
  CURRENT_TIMESTAMP() as timestamp,
  COUNT(*) as write_count
FROM INFORMATION_SCHEMA.SPANNER_STATISTICS
WHERE interval_end = CURRENT_TIMESTAMP()
  AND database_name = 'your_db'
  AND table_name = 'MyTable';
```

Monitor **CPU utilization per node** in Cloud Console - if one node is maxed out while others are idle, you have a hot shard.

**TL;DR:** Replace sequential IDs with randomized/hashed keys to distribute writes across all nodes.

# The Core Problem: HTTP Call Inside the Transaction

Spanner's `ReadWriteTransaction` uses **pessimistic locking with optimistic conflict detection**. Reads acquire shared locks, and the transaction holds them until commit. Anything that lengthens the transaction window increases the chance of:

1. **Lock contention** → other transactions abort yours (the `Aborted` errors)
2. **Latency spikes** → your transaction holds locks while waiting on a network call to the billing service
3. **Retry amplification** → Spanner retries the *entire closure*, meaning your HTTP call (and any side effect it has) runs again

The HTTP call is the smoking gun. It's slow, unpredictable, and almost certainly non-idempotent if it's a billing operation.

## What's Wrong, Concretely

```go
_, err := client.ReadWriteTransaction(ctx, func(ctx context.Context, txn *spanner.ReadWriteTransaction) error {
    // 1. Reads acquire locks ✅
    row, err := txn.ReadRow(ctx, "Accounts", spanner.Key{accountID}, []string{"Balance"})
    ...
    // 2. HTTP call holds locks for 100ms-2s ❌
    resp, err := billingClient.Charge(ctx, ...)
    ...
    // 3. Logging is fine, but if it's slow/blocking, same issue
    log.Printf("...")
    // 4. Commit
    return txn.BufferWrite(...)
})
```

The transaction closure can be retried by the Spanner client library on `Aborted`. Your billing call may be invoked multiple times — potential **double-charging**.

## Fixes

### 1. Get external work out of the transaction

Restructure to: read → external call → transaction (read-modify-write only).


```python
def prefix_to_range(prefix: str) -> tuple[str, str | None]:
    search = prefix.rstrip('%')
    
    if not search:
        return ("", None)  # Empty prefix = match all, no upper bound
    
    # Find last character that can be incremented
    chars = list(search)
    i = len(chars) - 1
    while i >= 0 and chars[i] == '\uffff':  # Max Unicode char
        i -= 1
    
    if i < 0:
        return (search, None)  # All max chars, no upper bound needed
    
    chars[i] = chr(ord(chars[i]) + 1)
    end = ''.join(chars[:i+1])
    return (search, end)
```

## Schema Design: Orders + OrderItems

This is a classic co-location problem. Here's a breakdown of your options:

---

## Option 1: Interleaving (e.g., Spanner, Bigtable-style)

```sql
-- Cloud Spanner example
CREATE TABLE Orders (
  OrderId    INT64 NOT NULL,
  CustomerId INT64,
  OrderDate  TIMESTAMP,
) PRIMARY KEY (OrderId);

CREATE TABLE OrderItems (
  OrderId    INT64 NOT NULL,
  ItemId     INT64 NOT NULL,
  ProductId  INT64,
  Quantity   INT64,
  Price      NUMERIC,
) PRIMARY KEY (OrderId, ItemId),
  INTERLEAVE IN PARENT Orders ON DELETE CASCADE;
```

**How it works:** Child rows are physically stored *adjacent* to their parent row on disk.

### Pros
- ✅ Single I/O to read an Order + all its Items (they're co-located)
- ✅ Eliminates join overhead for the common read path
- ✅ Atomic writes to parent + children without distributed transactions

### Cons
- ❌ Only available in specific databases (Spanner, some others)
- ❌ Items can't exist without a parent — tight coupling
- ❌ Hotspots if one order has thousands of items
- ❌ Harder to query OrderItems independently across orders

---

## Option 2: Foreign Key with Composite Index (Most Databases)

```sql
CREATE TABLE Orders (
  order_id    BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  customer_id BIGINT        NOT NULL,
  order_date  TIMESTAMPTZ   NOT NULL,
  status      TEXT          NOT NULL
);

CREATE TABLE OrderItems (
  item_id    BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  order_id   BIGINT  NOT NULL REFERENCES Orders(order_id) ON DELETE CASCADE,
  product_id BIGINT  NOT NULL,
  quantity   INT     NOT NULL,
  price      NUMERIC(10,2) NOT NULL
);

-- Critical: index the FK column for join performance
CREATE INDEX idx_orderitems_order_id ON OrderItems(order_id);
```

**Typical query:**
```sql
SELECT o.*, oi.*
FROM Orders o
JOIN OrderItems oi ON oi.order_id = o.order_id
WHERE o.order_id = $1;
```

### Pros
- ✅ Works everywhere (Postgres, MySQL, SQL Server, etc.)
- ✅ Referential integrity enforced by the DB
- ✅ Flexible — query items independently or joined
- ✅ Well-understood, easy to maintain

### Cons
- ❌ Requires a join (though indexed joins are fast)
- ❌ Two separate I/Os unless the query planner is smart
- ❌ FK checks add slight write overhead

## Option 3: Denormalization / JSON Column

```sql
CREATE TABLE Orders (
  order_id    BIGINT PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  customer_id BIGINT       NOT NULL,
  order_date  TIMESTAMPTZ  NOT NULL,
  items       JSONB        NOT NULL  -- embed items directly
);
```

```json

    {"product_id": 42, "quantity": 2, "price": 19.99},
    {"product_id": 17, "quantity": 1, "price": 5.49}

}
```

### Pros
- ✅ Single row read — zero joins
- ✅ Schema flexibility (items can vary in structure)
- ✅ Great for append-only / immutable orders

### Cons
- ❌ Hard to query/aggregate across items (e.g., "all orders containing product X")
- ❌ No referential integrity on embedded data
- ❌ Updating a single item requires rewriting the whole document
- ❌ Can hit row size limits with large orders

## Short answer

**Interleave `OrderItems` in `Orders`.** Your access pattern ("almost always read together") is exactly the use case interleaving was designed for. A foreign key gives you referential integrity but no locality benefit.

---

## What interleaving actually does

Without interleaving, Spanner stores `Orders` and `OrderItems` in separate key ranges, potentially on different splits (servers). A join requires a distributed lookup.

With interleaving, each `OrderItem` row is physically stored *immediately after* its parent `Order` row on disk:

```
Orders(order_id=1)
  OrderItems(order_id=1, item_id=1)
  OrderItems(order_id=1, item_id=2)
Orders(order_id=2)
  OrderItems(order_id=2, item_id=1)
  ...
```

A read of one order and all its items hits a single contiguous key range on a single split — one RPC, no cross-server coordination.

---

## The DDL

```sql
CREATE TABLE Orders (
  OrderId   STRING(36) NOT NULL DEFAULT (NEW_UUID()),
  CustomerId STRING(36) NOT NULL,
  CreatedAt  TIMESTAMP NOT NULL OPTIONS (allow_commit_timestamp = true),
  Status     STRING(32) NOT NULL,
  -- other columns
) PRIMARY KEY (OrderId);

CREATE TABLE OrderItems (
  OrderId   STRING(36) NOT NULL,
  ItemId    STRING(36) NOT NULL DEFAULT (NEW_UUID()),
  ProductId STRING(36) NOT NULL,
  Quantity  INT64      NOT NULL,
  UnitPrice NUMERIC    NOT NULL,
  -- other columns
) PRIMARY KEY (OrderId, ItemId),
  INTERLEAVE IN PARENT Orders ON DELETE CASCADE;
```

Key decisions in this DDL:

- **`NEW_UUID()` for `OrderId`** — random distribution prevents write hotspots. Never use a sequential integer or timestamp as the leading key.
- **`OrderId` leads both PKs** — required for interleaving; the child PK must be a prefix extension of the parent PK.
- **`ON DELETE CASCADE`** — deleting an `Order` automatically deletes its `OrderItems`. Without this, you must delete children before the parent or you get a constraint error.
- **`ItemId` as a UUID, not a sequence** — `(1, 2, 3, ...)` per order is fine at low volume, but a UUID is safer if you ever insert items in parallel.

---

## Querying interleaved tables

Because the rows are co-located, this join is served from a single split with no network hop:

```sql
SELECT
  o.OrderId,
  o.Status,
  oi.ProductId,
  oi.Quantity,
  oi.UnitPrice
FROM Orders AS o
JOIN OrderItems AS oi USING (OrderId)
WHERE o.OrderId = @orderId;
```

For bulk reads in Go, use a `KeySet` with a key prefix — this is more efficient than a SQL join when you're fetching a known set of orders:

```go
// Read one order and all its items in a single range read
keySet := spanner.Key{"order-uuid-here"}.AsPrefix()
iter := txn.Read(ctx, "OrderItems", keySet,
    []string{"OrderId", "ItemId", "ProductId", "Quantity", "UnitPrice"})
defer iter.Stop()
```

## Tradeoffs at a glance

| | Interleave | Foreign Key Only | No Constraint |
|---|---|---|---|
| **Read locality** | ✅ Co-located on disk | ❌ Separate splits | ❌ Separate splits |
| **Join cost** | ✅ Local, single split | ⚠️ Distributed | ⚠️ Distributed |
| **Referential integrity** | ✅ Enforced by Spanner | ✅ Enforced by Spanner | ❌ App responsibility |
| **Cascade delete** | ✅ `ON DELETE CASCADE` | ✅ `ON DELETE CASCADE` | ❌ Manual |
| **Reversible** | ❌ **Permanent** | ✅ Can drop/add | ✅ N/A |
| **Independent scaling** | ⚠️ Tied to parent splits | ✅ Separate splits | ✅ Separate splits |
| **Write to child without parent** | ❌ Parent must exist | ❌ Parent must exist | ✅ Unconstrained |
| **Max depth** | ⚠️ 7 levels total | Unlimited | Unlimited |

### When *not* to interleave

- **`OrderItems` is queried independently at high volume** (e.g., a reporting pipeline that scans all items across all orders). Interleaving ties item distribution to order distribution — you lose the ability to spread item-only scans across more splits.
- **The child table is much larger than the parent and grows unboundedly.** Very large child sets per parent can create split pressure on the parent's key range.
- **You need to move child rows between parents.** Interleaved rows cannot be re-parented — you'd have to delete and re-insert.
- **You're unsure about the access pattern.** If items are sometimes queried without orders (analytics, inventory), a foreign key gives you integrity without locking in the physical layout.

---

## Recommendation for your case

Given "almost always read together," interleave. The locality benefit is real and measurable — it eliminates a distributed join on every order detail page load. Use `ON DELETE CASCADE` so order deletion stays simple. Just make sure you're comfortable with the permanence before running the DDL in production.

# Interleaving vs Foreign Keys for Orders/OrderItems

This is a great question because the answer depends on your specific access patterns. Here's the breakdown:

## Interleaving

**How it works:** OrderItems are physically stored as child rows under their parent Order, creating a hierarchical structure.

**Pros:**
- **Single read operation** for order + items (no join needed)
- **Better locality** - related data stored together, fewer disk seeks
- **Atomic transactions** across parent/child by default
- **Efficient range queries** - "get all items for orders 100-110"
- **Natural for hierarchical data** - reflects your domain model

**Cons:**
- **Less flexible** - harder to query items independently
- **Slower updates** to items if they're large (may need to rewrite parent row)
- **Can't easily reparent** items to different orders
- **Limited to one parent** - items can't belong to multiple orders

## Foreign Key (Standard Normalization)

**How it works:** OrderItems table has an `order_id` column referencing Orders.

**Pros:**
- **Maximum flexibility** - query items independently, join as needed
- **Easier updates** - modify items without touching parent
- **Can reparent** items if needed
- **Works with multiple parents** if requirements change

**Cons:**
- **Requires a join** to read together (extra operation)
- **Worse locality** - data scattered across storage
- **More complex queries** - need explicit JOIN syntax

## Recommendation

**Use interleaving if:**
- Items are almost always read with their parent order
- Items are rarely queried independently
- You're using a database that supports it well (Cloud Spanner, some NoSQL databases)
- Your access pattern is truly hierarchical

**Use foreign keys if:**
- You need flexibility (query items alone, reparent, etc.)
- You're using traditional SQL (PostgreSQL, MySQL, etc.)
- You want simpler schema evolution
- You're uncertain about future requirements

## Practical Example

```sql
-- Interleaved (Cloud Spanner style)
CREATE TABLE Orders (
  order_id INT64,
  customer_id INT64,
  order_date TIMESTAMP,
  PRIMARY KEY (order_id)
);

CREATE TABLE OrderItems (
  order_id INT64,
  item_id INT64,
  product_id INT64,
  quantity INT64,
  PRIMARY KEY (order_id, item_id),
  INTERLEAVE IN PARENT Orders
);

-- Single efficient read
SELECT o.*, i.* FROM Orders o
JOIN OrderItems i USING (order_id)
WHERE o.order_id = 123;
```

```sql
-- Foreign Key (traditional SQL)
CREATE TABLE Orders (
  order_id INT PRIMARY KEY,
  customer_id INT,
  order_date TIMESTAMP
);

CREATE TABLE OrderItems (
  item_id INT PRIMARY KEY,
  order_id INT REFERENCES Orders(order_id),
  product_id INT,
  quantity INT,
  INDEX (order_id)
);

-- Same query, but with explicit join
SELECT o.*, i.* FROM Orders o
JOIN OrderItems i ON o.order_id = i.order_id
WHERE o.order_id = 123;
```

## Middle Ground: Denormalization

If you're using traditional SQL and reads are truly the bottleneck, consider:
- **Caching** the order + items together in Redis
- **Materialized views** for common queries
- **Selective denormalization** (store item count on Order, but not full items)

**For most applications, start with foreign keys** (simpler, more flexible) and only optimize to interleaving if profiling shows it's a bottleneck.

# Interleaving vs. Foreign Keys for Orders/OrderItems

This is a textbook case where **interleaving is the right choice**, but only if you understand the permanent tradeoff.

## Quick Answer

**Interleave `OrderItems` in `Orders`** if:
- OrderItems are almost always read/written together with their parent Order (your case ✓)
- You want CASCADE delete (orphaned items are a bug)
- You can afford the schema to be permanent (you cannot un-interleave later)

**Use a foreign key instead** if:
- OrderItems might be queried independently of Orders
- You need schema flexibility (might un-interleave in the future)
- You're unsure about the access pattern

## The Tradeoffs

| Aspect | Interleave | Foreign Key |
|---|---|---|
| **Locality** | OrderItems rows stored physically near parent Order rows | Rows scattered across the keyspace |
| **Join cost** | Local (no distributed join); nearly free | Distributed join; more participants, higher latency |
| **Cascade delete** | `ON DELETE CASCADE` is automatic and efficient | Manual cleanup or FK constraint (slower) |
| **Schema flexibility** | **Permanent.** Cannot un-interleave after table exists with data | Reversible; can add/remove at any time |
| **Query independence** | OrderItems queries must include parent key in predicate | OrderItems can be queried without knowing parent |
| **Depth limit** | Max 7 levels of nesting; OrderItems at level 2 is fine | No depth limit |
| **Index complexity** | Interleaved indexes inherit parent key; more natural | Secondary indexes are independent |
| **Write hotspots** | If Order PK is monotonic, OrderItems inherit the hotspot | Same risk, but easier to fix (just drop FK) |

## Recommended Schema

```sql
CREATE TABLE Orders (
  OrderId STRING(36) NOT NULL DEFAULT (NEW_UUID()),
  CustomerId STRING(36) NOT NULL,
  OrderTime TIMESTAMP NOT NULL,
  Status STRING(20) NOT NULL,
  PRIMARY KEY (CustomerId, OrderTime DESC, OrderId)
) PARTITION BY RANGE (CustomerId);

CREATE TABLE OrderItems (
  OrderId STRING(36) NOT NULL,
  ItemSeq INT64 NOT NULL,
  Sku STRING(50) NOT NULL,
  Quantity INT64 NOT NULL,
  UnitPrice NUMERIC NOT NULL,
  PRIMARY KEY (OrderId, ItemSeq),
  CONSTRAINT fk_order FOREIGN KEY (OrderId) REFERENCES Orders (OrderId)
    ON DELETE CASCADE
) INTERLEAVE IN PARENT Orders ON DELETE CASCADE;

-- Interleaved index for "all items for this order, newest first"
CREATE INDEX OrderItemsByTime ON OrderItems (
  OrderId,
  OrderTime DESC
) INTERLEAVE IN PARENT Orders;
```

### Why This Design

1. **Orders PK: `(CustomerId, OrderTime DESC, OrderId)`**
   - `CustomerId` first: co-locates all orders for a customer
   - `OrderTime DESC`: newest orders first (common query pattern)
   - `OrderId`: unique suffix (UUIDs avoid hotspots)
   - Avoids monotonic leading column (no hotspot)

2. **OrderItems PK: `(OrderId, ItemSeq)`**
   - `OrderId` first: all items for an order are adjacent
   - `ItemSeq`: natural ordering within the order
   - Interleaved in Orders: physically stored under the parent

3. **Cascade delete: `ON DELETE CASCADE`**
   - When an Order is deleted, all OrderItems are automatically removed
   - No orphaned rows; no manual cleanup

4. **Interleaved index on `OrderTime`**
   - If you query "items from orders after 2024-01-01", the index lets you seek without scanning all items

## When NOT to Interleave

```sql
-- ❌ DON'T do this if OrderItems are queried independently:
-- "Give me all items with SKU='WIDGET' across all orders"
-- This query must scan the entire OrderItems table anyway,
-- so interleaving doesn't help and locks you into the schema.

-- ✓ DO use a foreign key instead:
```

## Common Mistakes

### ❌ Mistake 1: Monotonic Order PK
```sql
-- HOTSPOT: all new orders pile onto one split

  OrderId INT64 NOT NULL AUTO_INCREMENT,
  CustomerId STRING(36) NOT NULL,
```

```sql
CREATE TABLE Orders (
  OrderId STRING(36) NOT NULL DEFAULT (NEW_UUID()),

```


### ❌ Mistake 3: Trying to Un-Interleave
Once OrderItems is interleaved and holds production data, you **cannot** undo it. The only way out is:
1. Create a new non-interleaved table
2. Copy all data
3. Swap table names (downtime)

**Lesson:** If you're unsure, start with a foreign key. You can always interleave later (same migration cost), but you can never un-interleave.

Great question — this is a classic Spanner schema design decision. Short answer: **interleave them**, but let's go through the tradeoffs so you know why and when you'd choose otherwise.

## Option 1: Interleaved tables (recommended for your case)

```sql
CREATE TABLE Orders (
  OrderId INT64 NOT NULL,
  CustomerId INT64,
  CreatedAt TIMESTAMP,
  ...
) PRIMARY KEY (OrderId);

CREATE TABLE OrderItems (
  OrderId INT64 NOT NULL,
  ItemId  INT64 NOT NULL,
  Sku STRING(MAX),
  Quantity INT64,
  ...
) PRIMARY KEY (OrderId, ItemId),
  INTERLEAVE IN PARENT Orders ON DELETE CASCADE;
```

**Pros:**
- **Co-location**: child rows are physically stored next to the parent row in the same split. Reading an order + its items is a single seek, often a single RPC.
- **Cheaper joins**: Spanner can do a local join without crossing splits.
- **Cascading deletes**: `ON DELETE CASCADE` is built in.
- **Implicit referential integrity**: you can't insert an OrderItem without an existing Order.

**Cons:**
- **Locked-in hierarchy**: OrderItems' primary key *must* start with `OrderId`. You can't reparent an item to another order without delete+insert.
- **Hot parents**: if a single Order gets enormous (thousands of items being written concurrently), you can hot-spot a split. Not typical for orders.
- **Limited interleaving depth** (7 levels) and the parent key prefix is fixed.

## Option 2: Foreign key (no interleaving)

```sql
CREATE TABLE OrderItems (
  ItemId INT64 NOT NULL,
  OrderId INT64 NOT NULL,
  ...
  FOREIGN KEY (OrderId) REFERENCES Orders(OrderId)
) PRIMARY KEY (ItemId);
```

**Pros:**
- Independent physical layout; OrderItems can be sharded by their own key.
- Easier to reparent or have items belong to multiple parents (with a join table).
- Good if items are *more often* read independently of orders.

**Cons:**
- Reads of "order + items" likely cross splits → more RPCs, higher latency.
- FK constraint adds a check on writes.
- No cascade delete (you must delete children explicitly, or use `ON DELETE CASCADE` if your DB supports it — Spanner added FK cascade support relatively recently).

## Option 3: Denormalize items into Orders (e.g., ARRAY<STRUCT>)

Only works if items are small, bounded in number, never queried individually, and updated atomically with the order. For most real-world ordering systems this is too restrictive — you'll want to query/aggregate items, update quantities, etc. Skip it.

## Recommendation for your scenario

# Interleave OrderItems in Orders

For your access pattern — child rows almost always read with the parent — **interleave**. This is exactly the case Spanner's interleaving was designed for.

## Recommended schema (GoogleSQL)

```sql
CREATE TABLE Orders (
  OrderId      STRING(36) NOT NULL DEFAULT (GENERATE_UUID()),
  CustomerId   STRING(36) NOT NULL,
  CreatedAt    TIMESTAMP NOT NULL OPTIONS (allow_commit_timestamp=true),
  Status       STRING(32) NOT NULL,
  TotalCents   INT64 NOT NULL,
) PRIMARY KEY (OrderId);

CREATE TABLE OrderItems (
  OrderId      STRING(36) NOT NULL,   -- must match parent's PK prefix
  ItemId       INT64 NOT NULL,        -- or STRING/UUID; unique within an order
  Sku          STRING(64) NOT NULL,
  Quantity     INT64 NOT NULL,
  PriceCents   INT64 NOT NULL,
) PRIMARY KEY (OrderId, ItemId),
  INTERLEAVE IN PARENT Orders ON DELETE CASCADE;
```

Key points:

- `OrderItems`'s PK **must** start with the parent's full PK (`OrderId`), then add its own discriminator (`ItemId`).
- `ON DELETE CASCADE` means deleting an `Order` row deletes its items in the same transaction — no orphan cleanup logic.
- `OrderId` is a UUID (`GENERATE_UUID()`), so writes spread across splits — no hotspot.

## Why interleave for this access pattern

| Benefit | What it gets you |
|---|---|
| **Physical co-location** | An `Order` and its `OrderItems` live in the same split, adjacent on disk. The "fetch order + items" read is a single local range scan. |
| **Cheap join** | `Orders JOIN OrderItems USING (OrderId)` becomes a local merge — no cross-split RPC fan-out. |
| **Single-participant transactions** | Writing an order + its items in one `ReadWriteTransaction` touches one split, so commit is fast and rarely aborts under contention. |
| **Atomic cascade delete** | `DELETE FROM Orders WHERE OrderId = @id` removes the items too, in one transaction. |

## Tradeoffs you're accepting

1. **Permanent decision.** You cannot un-interleave a table once it has data. If `OrderItems` later needs to exist without an `Order` (drafts, templates, transferred between orders), you'd be stuck.
2. **Parent must exist first.** You cannot insert an `OrderItem` before its `Order`. Usually fine — just insert both in the same transaction or use a single batched mutation.
3. **Interleave depth limit of 7.** Not a concern for two levels, but if you later want `OrderItems → Shipments → ShipmentEvents → ...`, count your levels.
4. **Hot order = hot split.** If one order receives thousands of item updates per second (unlikely for orders, common for, say, a chat room's messages), you'll hotspot on that order's split. Order workloads don't have this shape.
5. **Item count per order should be bounded.** Spanner has no hard limit, but a single order with millions of items defeats the locality benefit and creates a fat row range. For typical e-commerce (tens of items), no issue.

## When you'd pick FOREIGN KEY instead

```sql
CREATE TABLE OrderItems (
  ItemId       STRING(36) NOT NULL DEFAULT (GENERATE_UUID()),
  OrderId      STRING(36) NOT NULL,
  ...
  FOREIGN KEY (OrderId) REFERENCES Orders (OrderId),
) PRIMARY KEY (ItemId);
```

Choose this if **any** of these apply:

- You're not sure yet whether items are always co-accessed with orders (FK is reversible; interleave is not).
- Items legitimately exist independently of an order, or move between orders.
- You query items globally far more often than per-order (e.g., "all items with SKU X across all orders") — though a secondary index on `Sku` works either way.
- The parent-child relationship might change shape during the product's lifetime.

FK gives you referential integrity without the permanence and without the locality. You pay with cross-split joins and distributed transactions for the order+items write.

## What I would not do

- **Don't use a single denormalized `Orders` table with a `Items ARRAY<STRUCT<...>>` column.** It works for tiny, append-only item lists, but you lose the ability to index/query items, and updating one item rewrites the whole row.
- **Don't lead `Orders.OrderId` with a timestamp or sequence.** UUIDs (or `GENERATE_UUID()` / a bit-reversed `IDENTITY`) are the right call here — order creation is naturally monotonic in time, which is exactly the hotspot pattern to avoid.

## Bottom line

Your stated access pattern ("OrderItems will almost always be read together with their parent Order") is the textbook interleave case. Do it, with `ON DELETE CASCADE`, and use UUID order IDs. Accept the permanence — if your data model is genuinely as described, you won't regret it. If you're uncertain about the relationship's shape, start with a foreign key and migrate later (creating a new interleaved table and backfilling is straightforward; the reverse is not).

## The fix: bounded-staleness reads

### Single read (most common for a widget)

```go
import (
    "context"
    "time"
    "cloud.google.com/go/spanner"
)

func recentActivity(ctx context.Context, client *spanner.Client, userID string) ([]*Activity, error) {
    // Served by the nearest replica; no leader contact needed.
    txn := client.Single().WithTimestampBound(
        spanner.MaxStaleness(15 * time.Second),
    )

    stmt := spanner.Statement{
        SQL: `
            SELECT ActivityId, UserId, Kind, OccurredAt
            FROM   UserActivity
            WHERE  UserId = @userId
            ORDER BY OccurredAt DESC
            LIMIT 25`,
        Params: map[string]interface{}{
            "userId": userID,
        },
    }

    iter := txn.Query(ctx, stmt)
    defer iter.Stop() // always required — leaks a session if omitted

    var results []*Activity
    err := iter.Do(func(row *spanner.Row) error {
        var a Activity
        if err := row.ToStruct(&a); err != nil {
            return err
        }
        results = append(results, &a)
        return nil
    })
    return results, err
}
```

`MaxStaleness(15s)` tells Spanner "serve this from any replica whose data is at most 15 seconds old." The client library automatically routes to the nearest replica.

# Speeding Up Reads in Multi-Region Spanner

You're hitting the leader region because your query is using the default **strong consistency** read mode. For a "recent activity" widget, you can trade strict freshness for **lower latency and reduced load on the leader** by using a **stale read** with a bounded staleness bound.

## The Fix: Use `WithTimestampBound`

In your Go code, replace a strong-consistency read with:

```go
// Instead of:
row, err := client.Single().ReadRow(ctx, "Activity", spanner.Key{userID}, columns)

// Use:
row, err := client.Single().
    WithTimestampBound(spanner.MaxStaleness(10 * time.Second)).
    ReadRow(ctx, "Activity", spanner.Key{userID}, columns)
```

Or for a query:

```go
iter := client.Single().
    WithTimestampBound(spanner.MaxStaleness(10 * time.Second)).
    Query(ctx, spanner.NewStatement("SELECT ... FROM Activity WHERE ..."))
defer iter.Stop()
```

## Why This Works

- **`MaxStaleness(d)`**: Spanner picks a timestamp up to `d` in the past and reads from any replica that has caught up to that point. For a 10-second staleness window, Spanner can serve the read from a nearby regional replica instead of routing to the leader.
- **No locks, no aborts**: Stale reads never conflict with writes and never abort — they're purely read-only.
- **Lower latency**: A regional replica is often geographically closer than the leader region.
- **Reduced leader load**: Spreads read traffic across replicas.

## Choosing the Staleness Bound

| Bound | Use Case |
|---|---|
| `MaxStaleness(5s)` | Real-time dashboards, activity feeds where "a few seconds old" is acceptable |
| `MaxStaleness(30s)` | Analytics, reporting, widgets that refresh infrequently |
| `MaxStaleness(1m)` | Caches, background jobs, non-critical data |
| `ExactStaleness(t)` | Testing; rarely used in production |
| `MinReadTimestamp(t)` | "Read at least as fresh as this timestamp" (e.g., after a write) |
| No bound (default) | Strong consistency; always hits the leader |

For a "recent activity" widget, **10–30 seconds is typical**.

## Why the Full Scan Happens


The optimizer won't use your index for a few common reasons:

### 1. You're doing `SELECT *` (most likely culprit)

The "simplest, fewest-lines" SQL would be:
